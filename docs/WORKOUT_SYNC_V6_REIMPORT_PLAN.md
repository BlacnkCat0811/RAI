# RAI Workout v6 全量重传与同步优化方案

**状态为待实施。** 依据 2026-11-10 的决定，Workout 同步只保留 v6，在空白数据库和全新 iOS 会话中从 HealthKit 重传。旧数据、旧队列和旧回执退出新系统。本文记录实施顺序、协议约束和验收条件。

依据 [v6 合同](../contracts/sync-v6.md)、[同步审查证据](IMPLEMENTATION.md#同步设计与实现审查2026-11-10) 和 [独立会话合同](PHASE5A_NEW_SESSION.md)。

2026-11-10 补充边界：上传的 HealthKit 对象 UUID 仅保留顶层 `workoutID` 一次；活动分段、标量、series 和路线不上传各自 UUID，不重复 Workout UUID。数据库所需的子对象身份由服务端生成。用户另已明确要求仅前台点击上传、最终显示上传成功或失败，并去掉客户端后台上传和恢复；下文原重传流程保留为历史方案，其中 Outbox、自动恢复和多阶段同步 UI 条目不再代表新的客户端目标，手动上传流程尚待实施。

## 1. 重传边界

| 对象 | 新系统处理 |
| --- | --- |
| Workout、关联样本、series、路线 | 从当前 HealthKit 可见范围重读。Workout 仍按现有 Apple Watch 来源策略准入。 |
| 日常健康事实和 VO₂ | 使用各自现行接口，从新会话的空 anchor 开始。各自按其回执推进游标。 |
| 训练计划、反馈、手工参考值和设置 | 这些是 RAI 业务数据，HealthKit 重传范围之外。新系统从空状态开始，仍需使用的手工数据在新系统录入。 |
| 分析、训练负荷和 Readiness | 基于新入库事实重新生成。界面按实际状态显示等待、覆盖不足或可用。 |
| 旧同步状态 | 旧 v3/v4/v5 入口、解码器、队列、接收回执、墓碑、游标、文件和 Keychain 身份均退出新会话。新事实 UUID 按现行规则从新 datasetID 派生，删除屏障按新 dataset 隔离。 |

HealthKit 已删除、当前授权不可见或 Apple 已不再返回的记录无法从本轮重传恢复。服务器历史上删除过、目前仍可见且合格的 Workout 会按新数据集规则重新导入。

旧版待办排空、历史载荷分析兼容和旧 Outbox 升级修复从实施范围移除。保留管理删除及当前 v6 的防复活保证。原架构方案和旧合同保留为工程历史。

## 2. 实施顺序

| 阶段 | 交付 | 放行条件 |
| --- | --- | --- |
| A. 接收与提交 | v6 严格信封、精确原字节、已知字段投影、原子事实事务、失败重试和管理删除 | 隔离 PostgreSQL 上的故障、重放、删除与围栏用例通过 |
| B. iOS 重传 | 独立会话、历史分批发现、组包质量门槛、后台恢复、可观察进度 | Simulator 经本机 HTTP 和隔离 PG 跑通首包、丢 ACK、进程中断和同 UUID 重放 |
| C. 分析覆盖 | v6 专用覆盖证明、更新 Readiness 依赖和产品提示 | 证明可续期，缺失证据时指标如实降级 |
| D. 切换演练 | 空库初始化、独立真机验收、重传收尾对账、运行门禁 | 真机重传证据完整，仍有阻塞项时保留明确状态 |

A 与 B 是开启正式重传的门槛。C 是将 Readiness 标为可用的门槛，可以与 D 的准备并行。开发和验收均在本机 Mac 上执行。

## 3. 服务端接收与提交

### 3.1 一个上传入口，两种回执

- 握手继续声明 `workoutPayloadVersion=6` 和 `workoutUUIDIngestVersion=1`。Workout 写入只走 `POST /v2/sync/workout-ingests/{workoutID}`，同路径 GET 查询状态。会话握手、daily 和 VO₂ 各自按本身的合同校验。
- 新包在短接收事务中按 `(dataset_id, workout_uuid)` 写入 `workout_ingests.raw_json bytea`。原文是解压后的 JSON，空白、键顺序和未知值均逐字节保存。提交后返回 `accepted` 和首次 `acceptedAt`。
- 同 UUID 重试经授权后返回原接收回执，原文、事实和待办保持幂等。GET 以根墓碑优先，然后读取 `accepted`、`committed` 或 `rejected`。只有明确的 `404 workout_ingest_not_found` 允许准备新包。新数据集若出现 Workout 已存在而接收行缺失，作为一致性故障告警。
- API 执行有界传输与信封校验。UTF-8、重复键、深度、必填身份、根来源及 Workout 核心错误在接收前返回明确错误。标量、series 与 route 数量限额在同一次词法遍历中累计，包含被软跳过的数组成员。超过限额返回 413。词法遍历使用 `UseNumber`，数值范围由对应已知字段单独判断。
- Worker 在事务外完成样本、series、路线和来源投影。事务内按既有 dataset 行锁复核身份、collector、删除屏障及有效租约，写事实、来源摘要、`change_events`、分析待办和最终回执，再更新接收行为 `committed`。事实 revision 由行锁控制。现有变更通知按 `(commit_rev, ordinal)` 续读。

**存储改动集中在原文和投影的分工。** `workout_ingests.raw_json` 持有精确原文。`workout_imports` 中用于分析、审计和回执的 JSONB 只写有类型的 v6 投影信息，例如根来源、版本和必要诊断，摘要仍以原始字节计算。分析和特征读取改用已投影事实及其来源标记。未知 `observation`、超范围数字和 PostgreSQL JSONB 无法表示的扩展值留在原文中。检查 `workout_imports.payload` 的所有读写方，给新格式补空库 schema 和受限角色测试。采用新增迁移文件，既有迁移及其校验值保持原样，迁移只用于初始化目标数据库和隔离测试库。

### 3.2 资源、失败与删除

- 起始预算沿用合同中的 32 MiB JSON、8 MiB gzip、100∶1 加 64 KiB 解压余量、50,000 个样本及组头、100 万 series 点、16 条路线、100 万路线点。保留每 dataset 200 条或 512 MiB 待解析上限和进程并发槽。iOS 与 API 按同一组边界验收。
- 将接收配额和插入放进独立于 dataset 行锁的每 dataset 短事务锁，可用 PostgreSQL 事务级 advisory lock。管理删除按固定顺序先锁 dataset 行，再取得同一接收锁，并在墓碑事务内清理原文和终结待处理任务。这样删除先行时接收看到墓碑，接收先行时删除能清理它。Worker 与删除仍由 dataset 行锁和租约约束。
- Worker 遇到数据库暂态错误或处理超时，退避后重试同一原包。达到自动重试上限时保持 `accepted`，暂停自动调度，并通过 `errorCode=processing_needs_attention` 通知客户端。管理路径在校验当前身份、墓碑和租约后可重新排队，保留单调 fencing token。确定无法投影的载荷才进入 `rejected`。
- 提供仅针对新 UUID 的接收暂停能力，用于切换演练与故障止血。握手如实反映开关，查询、接收回执重放和 Worker 处理继续工作。清理发布配置中已无效的旧模式变量。日志只记录计数、大小、耗时、错误码及脱敏关联标识。

## 4. iOS 全量重传

1. 复用独立 SyncSession 绑定与 prepared 恢复。新会话获得新的服务、dataset、collector 和设备身份，使用独立 Keychain、Outbox、后台传输标识和本地产品缓存。激活前二次核验握手，迟到回调归属原会话。
2. 从空 anchor 分批发现 Workout，耐久保存本地发现游标和待办。前台继续扫描与重传，启动后从已保存的游标继续。遍历到固定截止时间后给出本轮统计，再恢复增量发现。界面上最近 100 条的列表上限独立于历史重传扫描。
3. 先 GET 状态，再读取 Workout 明细。每次准备每种标量或 series 查询一次。对当前设备支持的流，成功查询且零条记录属于可见范围内的空结果。查询异常或路线读取中断则延后该 Workout，下一次准备时重试。已知坏点按合同跳过并记录诊断。条数、字节或路线数超过硬限额时终止组包，显示具体错误。用硬限额传递测试覆盖真实 HealthKit 适配器和组包器之间的错误映射。
4. 检查通过后序列化一次并原子写入 Outbox，持久记录 v6、会话身份和文件绑定。缓存 gzip 只从已校验的原文件派生，冷启动复用前检查其绑定。gzip 超出压缩大小或解压比、但明文满足限额时使用合同支持的明文 multipart。网络失败与杀进程恢复复用原始字节。
5. 接收回执耐久保存后才释放本地文件。分别展示「待采集」「待上传」「已接收」「已入库」「等待分析」「分析可用」及失败原因。已接收 UUID 只查状态。按服务端并发预算和 `Retry-After` 限速，完成页后继续调度下一页。
6. 固定本轮可见集合的统计口径。记录已提交、处理中、明确排除、待分类、读取失败和超限。完成条件为合格 Workout 全部 `committed`，且未决为零。增量同步按相同状态机继续。

首次快照以封包时 HealthKit 可见数据为准。随后到达的关联样本按当前 UUID 一次接收语义留在 HealthKit。Workout 顶层 Watch 来源证明根来源，子流的归属仅表明与该 Workout 关联。支持关联观测的算法可用该证据。需要独立设备来源的指标在证据不足时如实标记。

## 5. Readiness 覆盖证明

给现有 Workout completeness 控制面定义独立的 v6 证明版本，保持 Workout 单包及上传热路径不变。客户端在 Readiness 所需的有界时间窗中固定谓词、截止点和当前 collector，分批持久保存可见 Workout 清单、来源排除证据和 `committed` 回执关联。Workout 内各受支持流的采集结果使用 v6 的诊断字段。证明描述本轮可见范围，HealthKit 授权状态和绝对历史完整性保持未知。

服务端核对同一 dataset/collector epoch、清单覆盖窗口、合格 UUID 的真实回执、源策略和未决任务。分批提交使用固定清单身份和页序，最终证明在 dataset 行锁内核对事实 revision 后提交。同一证明重试返回原回执。新 Workout 入库或管理删除后，旧证明进入待更新状态，下一次增量补证推进截止点。用现行 Readiness 时间窗与新鲜度规则验证第二轮续期。首轮证明尚未达标时显示覆盖不足。

## 6. 验收与切换

| 验收项 | 通过条件 |
| --- | --- |
| v6 入口和隔离 | 握手和传输只接 v6 Workout。旧 token、epoch、会话文件和后台回调无法写入目标数据集。daily 与 VO₂ 独立验收。 |
| 原文和软跳过 | 合成包覆盖未知嵌套字段、`1e400`、`\u0000`、未知流、坏点和 `observation`，比较最终 bytea 与原文逐字节一致。已知事实可用，分析可读取，未知字段不产生事实。 |
| 原子性和删除 | 故障注入覆盖提交前后、同 UUID 并发、ACK 丢失、Worker 崩溃、租约过期、删除与接收两种锁顺序。事务回滚后无半成品，根墓碑阻止复活。 |
| iOS 读取与恢复 | 覆盖空流、单流失败、路线异常、上限与上限加一、明文与 gzip、后台恢复、冷启动和无变化重试。已接收 UUID 的新增明细查询、组包和 POST 均为零。 |
| 分析和证明 | v6 合成事实能发布实际分析结果。无证明、过期证明、未决 Workout 与混合来源的状态如实显示。合格证明支持第二轮增量续期。 |
| 性能 | 恢复 `syncperf`，用现有 `TestWorkoutUUIDIngestPerf` 作为本机 HTTP 测量基线，补 40 分钟常规包和密集长跑包。每种代表包至少 30 次计时，脚本校验用例命中、有效样本数与失败数，空跑或全跳过须失败。分别记录准备、收完请求到 ACK、ACK 到入库的 p50/p95。沿用待验证目标，代表包收完到 ACK 的 p95 小于 300 ms，dataset 行锁竞争下完整 POST 小于 500 ms。 |

按 `gate`、定向隔离 PostgreSQL、SwiftPM、Simulator、v6 本机 HTTP→PG 闭环和非 race 性能回归执行。合同修改需跑 `scripts/local/contracts.sh`。在切换前运行 `full`，记录设备、构建版本、用例结果和未验证项。真机验收在 Mac 上使用独立环境，输出限于计数、状态、时间与脱敏摘要。

实际切换顺序如下。

1. 为目标创建独立空白 PostgreSQL 数据库，初始化到验收通过的 schema，并使用 `rai init` 创建全新身份。确认 API、Worker、受限角色和握手版本。
2. 在 iPhone 上绑定独立新会话。用少量合格 Workout 验证接收、事实、分析、断网恢复与重复同步，再启动历史重传。
3. 固定本轮截止点，按 Workout 提交结果和日常事实/VO₂ 的各自回执对账。保留超限、暂态故障及待分类清单，处理完毕后继续增量。
4. 接收出现异常时暂停新 UUID，继续查状态并处理已接收原包。在同一 v6 目标上恢复。旧环境退出服务和物理清理作为单独操作执行，目标库已验收且清理对象已核对后再进行。

本轮仅交付方案。实施结果和验收证据续记到 [IMPLEMENTATION.md](IMPLEMENTATION.md)。
