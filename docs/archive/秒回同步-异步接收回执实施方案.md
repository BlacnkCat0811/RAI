# RAI「秒回」同步：异步接收回执实施方案

> **状态：提案，未实现。**
> 本文是独立立项文档，不改变当前已部署行为。实现前需完成第 11 节的待拍板项。
>
> - 目标 schema：`50`

> - 客户端：iOS 下一版
> - 关联文档：`docs/RQrun-HealthKit-上传协议.md`、`docs/IMPLEMENTATION.md`、`AGENTS.md`

## 0. 结论摘要

把一次 Workout 上传拆成**两个持久化点**：

1. **接收事务（目标 p95 < 300 ms 服务端处理；不含读 body）**
   原始 JSON 字节 + 接收回执 + 解析队列行，一次短事务提交。
2. **解析事务（当前约 8–11 s）**
   原有导入逻辑整体搬进 Worker：事实、删除屏障、提交日志、分析 job、最终回执，仍然一次事务提交。

客户端 POST 在**接收事务提交后**立即拿到 200 和 `ingestStatus=accepted`，不再等待 `series` 批量写入；随后轮询状态端点，等服务端异步解析完成。

关键工程决策：

- 接收表**不建 `datasets` 外键**，接收事务**不锁 `datasets` 行**。否则一个 10 秒的导入事务（`SELECT ... FOR UPDATE`）会把接收请求堵在 FK 的 `FOR KEY SHARE` 上，秒回就是假的。
- 不复用现有 `jobs` 表接收上传任务。`jobs` 有 `datasets` 外键，插入时同样会被 dataset 行锁阻塞；解析队列放在 `workout_ingests` 自己的行上，用 `FOR UPDATE SKIP LOCKED` 认领。
- 接收回执与最终回执是**两张不同的回执**：前者证明“字节已持久化”，后者证明“事实已提交”。二者都不允许互相冒充。
- v4 同步路径原样保留；新路径通过 handshake `workoutIngestVersion` 协商，旧客户端不受影响。

预期收益：

| 指标 | 现状 | 本方案后 |
|---|---|---|
| 服务器接收回执（请求体收完后） | 8–11 s | **目标 p95 < 1 s** |
| 两条首次同步 tap → “已上传” | 约 30–40 s | 约 **10–12 s**（两条构建可并发；若 HealthKit 串行化则接近 16–18 s） |
| 两条首次同步 tap → 事实提交 | 30–40 s | 约 12–20 s，但**不阻塞用户** |
| 重复同步同一批 | 0–2 s（前置修复后） | 0–2 s |
| 服务端解析失败 | 同步请求失败 | 200 已接收 + 状态 `rejected`，可诊断 |

> **“秒回”的边界**：本项目保证**服务器接收回执**秒回，不保证 tap → 全部完成秒回。
> 首次同步仍有 8–9 秒的 HealthKit 读取与 JSON 构建；要把它也压下去，见第 10 节阶段二。

## 1. 背景：现在为什么不是秒回

### 1.1 实测基线

一次 40 分钟跑步、约 685 KB 的 v4 bundle：

```
transport(multipart)      440 ms
gzip 解压                  28 ms
json_decode               293 ms
semantic_validation        53 ms
dataset_lock              0.9 ms
identity_checks           216 ms
sample_writes           1,025 ms
association_writes        948 ms
series                  7,942 ms   ← 75%
routes                    129 ms
dirty_job                   6.5 ms
receipt                    177 ms
commit                      6.5 ms
---------------------------------
import_total           10,556 ms
```

当前 [ImportWorkoutBundle](../../apps/server/internal/storage/postgres/workout_bundles.go) 在**同一个 HTTP 请求**里完成：

- 语义校验；
- 取 dataset 行锁；
- 墓碑/身份冲突检查；
- 写 workout、sample、association、series、route；
- 写 `dirty_scopes`、`analysis.workout` job、`change_events`；
- 写最终回执 `workout_imports`；
- 提交事务；
- 才返回 200。

所以客户端等待的是**整个数据库导入**，不是“文件上传完成”。

### 1.2 RQrun 的语义

`docs/RQrun-HealthKit-上传协议.md` 记录的是：

- 一次上传一条 Workout，multipart 约 641 KB；
- 服务端收到文件后立即返回 `{"syscode":200,"data":"<记录ID>"}`；
- 解析在服务端异步进行；
- App 之后轮询 `GET /Record/code_apple_source_status` 获取解析结果；
- 解析成功的 UUID 不再重复上传。

RQrun 的 200 是**文件接收回执**，RAI 的 200 是**事实提交回执**。两者的等待时间差，主要就是 `series` 那 8 秒。

### 1.3 三个不同的问题

| 问题 | 表现 | 归属 |
|---|---|---|
| A. 服务端 ACK 等待事务提交 | 8–11 s/条 | **本项目** |
| B. 客户端首次构建慢 | `v4_build_ms` 7.5–9.3 s/条 | 阶段二（可选） |
| C. 重复上传 | 7 分钟、9 次 POST、5 次幂等重传 | 前置修复（见 1.4） |

本项目只解决 A。A 解决后，C 如果还在，会把“秒回”再次拖成多次上传，所以 C 是**硬前置**。

### 1.4 前置修复（必须先合入）

1. **v4 `setBundle` 缺少 `discoveryGeneration` 与 `captureManifest`**
   [SyncCoordinator.swift](../../ios/RAI/App/SyncCoordinator.swift) 的 `syncV4` 只传了 file/sha256/boundary。
   `OutboxStore.acknowledgeBundle` 因此只能用 generation 0 判定覆盖，`deliveredGeneration` 停留在 0，`needsDelivery()` 一直为真，恢复流程反复重传。
   修法：v5 的 `setBundle` 必须像 v3 路径一样传 `discoveryGeneration` 和 `manifest`；并补一条“accept 后 watermark 前进、recovery 不再 POST”的测试。

2. **普通同步与“强制重新同步”没有分开**
   `syncWorkouts(_:)` 当前固定 `forceNewBundle: true`，每次点击都重建、重传。
   修法：普通同步 `forceNewBundle: false`，由 `isAlreadyDelivered` 跳过；另设显式的“重新同步检查迟到数据”动作。

这两条不解决，异步 ACK 只会把“每次 10 秒”变成“每次 1 秒，但重复很多次”。

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 | 验收口径 |
|---|---|---|
| G1 | 接收回执与解析解耦 | POST 在接收事务提交后返回，不等待事实写入 |
| G2 | 接收回执快 | 服务端 `ingest_accept_ms` p95 < 300 ms（理想 < 100 ms）；含请求体读取的 `ack_total_ms` p95 < 1 s（本地/正常宽带） |
| G3 | 接收不阻塞 | 当另一个事务持有 `datasets` 行锁 10 s 时，接收仍在 500 ms 内返回 |
| G4 | 解析契约不降级 | 事实、删除屏障、提交日志、分析 job、最终回执仍在同一事务提交 |
| G5 | 幂等 | 同字节重试返回同一接收回执，只产生一个解析任务、一次事实提交 |
| G6 | 删除优先 | 接收后、解析前发生删除，解析不得复活数据；状态为 `rejected/workout_deleted` |
| G7 | 客户端可恢复 | App 在 accept 后被杀，重启只轮询状态，不重读 HealthKit、不重传 |
| G8 | 旧客户端不受影响 | 未协商 v5 的客户端继续走 v4 同步路径 |
| G9 | 可观测 | 接收、排队、解析、拒绝各有指标与结构化日志，且不含健康值 |

### 2.2 非目标

- 不改变 HealthKit 读取字段、单位、来源策略与原始载荷格式。
- 不丢弃未知字段；原始字节仍是权威副本。
- 不把分析发布改成同步；分析本来就是异步的。
- 不改变删除语义，不做“快照缺席推断删除”。
- 不实现后台自动 HealthKit 同步（`HKObserverQuery`）——那是另一个项目。
- 不在本项目里优化 `series` 写入性能；它只影响“已接收 → 已入库”的后台时长，不影响 ACK。
- 不为了秒回而跳过身份冲突、墓碑、epoch/fencing 检查。

### 2.3 体验目标

| 场景 | 阶段一（本项目） | 阶段二（可选，构建优化） |
|---|---|---|
| tap → 服务器接收回执（2 条） | 10–12 s | 5–7 s |
| 接收回执本身 | < 1 s | < 1 s |
| 已接收 → 事实提交（2 条） | 12–20 s（后台） | 12–20 s（后台） |
| 重复同步同一批 | < 1 s | < 1 s |
| App 在 accept 后被杀 | 重启后只轮询 | 同左 |

## 3. 目标语义

### 3.1 两阶段持久化

```
┌──────────────┐
│ iOS 构建 bundle │  8–9 s（HealthKit 读取 + JSON 编码）
└──────┬───────┘
       │ POST multipart(gzip) 685 KB
       ▼
┌──────────────────────────────────────────────┐
│ 接收事务（短）                                  │
│  1. 词法/信封校验（不做完整投影）                 │
│  2. 校验 dataset / epoch / collector（只读）      │
│  3. INSERT workout_ingests(payload bytea, seq)   │
│  4. INSERT accept_receipt                        │
│  5. COMMIT                                       │
└──────┬───────────────────────────────────────┘
       │ 200 {"ingestStatus":"accepted","ingestID":...}
       ▼
┌──────────────────────────────────────────────┐
│ ingest worker（异步，可排队）                    │
│  1. 认领 ingest 行（FOR UPDATE SKIP LOCKED）      │
│  2. 完整解码 + 投影                              │
│  3. 取 dataset 行锁（此时才取）                   │
│  4. 墓碑/身份/删除屏障检查                        │
│  5. 写事实 + dirty + analysis job + change log   │
│  6. 写最终回执 workout_imports                    │
│  7. 更新 ingest 为 committed（fencing 校验）      │
│  8. COMMIT                                       │
└──────┬───────────────────────────────────────┘
       │
       ▼
客户端轮询 GET /v2/sync/workout-ingests/{id}
  accepted → committed | superseded | rejected
```

### 3.2 两张回执

**接收回执（不可变，POST 返回）**

```json
{
  "version": 1,
  "ingestID": "3f0d8f7e-6a1e-4f4b-a6e2-6a1c2d9b7e11",
  "workoutID": "8CEA80AE-FC92-470A-95EA-D01F11D53866",
  "bundleSHA256": "9f2c...e1",
  "ingestStatus": "accepted",
  "acceptedAt": "2026-11-09T10:21:33.412Z"
}
```

它证明：**这串字节已经持久化，解析任务已经排队**。不证明事实已经写入。

**最终回执（不可变，状态端点返回）**

```json
{
  "version": 1,
  "ingestID": "3f0d8f7e-6a1e-4f4b-a6e2-6a1c2d9b7e11",
  "workoutID": "8CEA80AE-FC92-470A-95EA-D01F11D53866",
  "bundleSHA256": "9f2c...e1",
  "ingestStatus": "committed",
  "commitRevision": 1842,
  "counts": { "...": "与现有 WorkoutImportCounts 相同" },
  "analysisStatus": "queued",
  "analysisJobIDs": ["..."],
  "acceptedAt": "2026-11-09T10:21:33.412Z",
  "committedAt": "2026-11-09T10:21:45.031Z"
}
```

它复用现有 `syncing.WorkoutImportReceipt` 的字段，额外加 `ingestID` / `acceptedAt` / `committedAt`。

### 3.3 状态机

```
accepted ──成功──▶ committed
   │
   ├──有更高 ingest_seq 的同 Workout 已提交──▶ superseded
   │
   ├──永久错误 / 重试耗尽──▶ rejected
   │
   └──worker 崩溃 / 租约过期──▶ 仍是 accepted，重新认领
```

| 状态 | 含义 | 客户端行为 |
|---|---|---|
| `accepted` | 字节已持久化，等待解析 | 不重传；轮询；可离开页面 |
| `committed` | 事实、回执、分析 job 已提交 | 视为原“durable ACK”；继续轮询分析 |
| `superseded` | 同 Workout 有更高 `ingest_seq` 的 bundle 已提交，本包不再投影 | 视为成功，不重传 |
| `rejected` | 解析永久失败或重试耗尽 | 停止自动重试；展示错误；按 `retryable` 决定“重试解析”或“重新同步” |

### 3.4 必须保持的不变量

1. **200 之前，原始字节必须已持久化。** 不允许“先回 200，再写库”。
2. **接收回执不得冒充最终回执。** 客户端不得在 `accepted` 时显示“分析完成”。
3. **最终回执必须与事实、删除屏障、提交日志、分析 job 同事务提交。**
4. **删除优先。** 解析事务在写事实前重新检查墓碑；接收后发生的删除必须赢。
5. **同字节只有一个 ingest、一个解析任务、一次事实提交。**
6. **同 Workout 多包按 `ingest_seq` 最新者胜。** 不允许旧包在解析乱序时覆盖新包。
7. **fencing 失败必须回滚事实。** 租约过期后，僵尸 worker 不得提交。
8. **未知字段不丢。** 原始字节保留；解析只投影已知字段。
9. **没有事实就没有分析。** 分析 job 只能在解析事务内创建。
10. **接收路径不等待解析锁。** 接收事务不取 `datasets` 行锁，也不插入带 `datasets` 外键的行。

### 3.5 契约修订

`AGENTS.md` 当前写的是：

> 原始事实、删除屏障、提交日志、分析待办及最终回执必须在同一事务提交。

建议改为：

> **接收事务**必须原子提交原始载荷、接收回执与解析待办；**解析事务**必须原子提交原始事实、删除屏障、提交日志、分析待办与最终回执。接收回执不得冒充最终回执，未提交事实不得标记为已解析。dataset 行锁产生**事实提交**顺序；接收顺序由 `ingest_seq` 记录，不构成下载水位。

同时保留：

- 上传不可变、同字节重试返回原接收回执；
- 删除优先，旧上传不得复活 UUID；
- 不做删除同步；
- 仅用合成数据测试；
- 事务变更必须跑真实隔离 PostgreSQL 集成测试。

## 4. 协议设计：ingest lane v1

### 4.1 能力协商

`GET /v2/handshake` 增加：

```json
{
  "capabilities": {
    "workoutIngestVersion": 1,
    "workoutIngestEndpoint": "/v2/sync/workout-ingests",
    "workoutIngestMaxBytes": 8388608,
    "workoutIngestMaxPending": 200,
    "workoutIngestMaxPendingBytes": 536870912
  }
}
```

- 旧服务端没有该字段，客户端保持 v4 同步路径。
- 客户端只在 `workoutIngestVersion >= 1` 时走新路径。
- 原始载荷仍是 `protocolVersion: 4`；变化只在 ACK 语义，不新增字段、不改单位。
- 不把 `X-RAI-Sync-Protocol` 直接升到 5，避免把“载荷版本”和“ACK 模式”混在一起。能力名独立，便于灰度与回滚。

### 4.2 POST /v2/sync/workout-ingests

请求与 v4 完全一致：

```http
POST /v2/sync/workout-ingests HTTP/1.1
Host: api.example
Authorization: Bearer <token>
Content-Type: multipart/form-data; boundary=rai.boundary.xxx

--rai.boundary.xxx
Content-Disposition: form-data; name="file"; filename="workout.json.gz"
Content-Type: application/gzip

<gzip JSON>
--rai.boundary.xxx--
```

- 表单字段名仍为 `file`。
- 传输仍为 gzip multipart；哈希仍绑定解压后的 JSON 字节。
- 鉴权、dataset/epoch/collector 校验与 v4 相同。
- 请求体上限沿用 v4 的 `MaxWorkoutBundleBytes` / wire / compressed 限制。

成功响应（200）：

```json
{
  "version": 1,
  "ingestID": "...",
  "workoutID": "...",
  "bundleSHA256": "...",
  "ingestStatus": "accepted",
  "acceptedAt": "..."
}
```

同步拒绝（不产生 ingest 行）：

| HTTP | 场景 |
|---|---|
| 400/422 | multipart/gzip/UTF-8/JSON 词法/信封身份不合法 |
| 403 | dataset 不属于当前 principal |
| 409 | dataset epoch 变化、collector 被 fencing、dataset retired |
| 413 | 超过 bundle/route/series 上限（信封可判定的部分） |
| 429 | 上传并发或积压配额满，带 `Retry-After` |
| 503 | 接收事务暂时不可用 |

> 注意：**Workout 核心字段、来源策略、完整投影是否合法，属于异步解析错误**，不在接收阶段返回。
> 这是 RQrun 的模型：先收文件，再报解析结果。接收阶段只拒绝“连信封都不成立”的包。

### 4.3 GET /v2/sync/workout-ingests/{ingestID}

响应 200：

```json
{
  "version": 1,
  "ingestID": "...",
  "workoutID": "...",
  "bundleSHA256": "...",
  "ingestStatus": "accepted",
  "attempts": 1,
  "acceptedAt": "...",
  "updatedAt": "...",
  "errorCode": null,
  "retryable": false
}
```

`committed` 时追加：

```json
{
  "ingestStatus": "committed",
  "commitRevision": 1842,
  "counts": { "...": "..." },
  "analysisStatus": "queued",
  "analysisJobIDs": ["..."],
  "committedAt": "..."
}
```

`rejected` 时：

```json
{
  "ingestStatus": "rejected",
  "errorCode": "workout_identity_conflict",
  "retryable": false,
  "attempts": 3,
  "finishedAt": "..."
}
```

`superseded` 时：

```json
{
  "ingestStatus": "superseded",
  "supersededBy": "<更高 ingest_seq 的 ingestID>",
  "finishedAt": "..."
}
```

- 只允许查询当前 principal 所属 dataset 的 ingest。
- 不返回原始载荷、GPS、心率或任何样本值。
- `ingestID` 是 UUIDv4，仍必须做 dataset 作用域校验，不能只靠不可猜。

### 4.4 幂等与重试规则

| 场景 | 服务端行为 | 客户端行为 |
|---|---|---|
| 同 dataset + 同 workout + 同 sha 重复 POST | 返回已存在的接收回执；不新增解析任务 | 视为成功，不再重传 |
| 同 workout + 不同 sha | 新建 ingest，新 `ingest_seq`；两者都可解析，最新者胜 | 正常上传 |
| POST 时已 committed | 返回同一接收回执；状态端点返回 committed | 不再重传 |
| POST 时已 superseded | 返回同一接收回执；状态端点返回 superseded | 视为成功 |
| POST 时已 rejected 且 `retryable=false` | 返回同一接收回执；状态端点仍 rejected | 不自动重传；需“重新同步”生成新包 |
| POST 时已 rejected 且 `retryable=true` | 默认返回 rejected；客户端显式带 `X-RAI-Ingest-Retry: 1` 时重置为 accepted 并重新排队（有次数上限；载荷已被 GC 则拒绝） | 展示“重试解析”动作 |
| 接收后响应丢失 | 同字节重试拿回同一接收回执 | 重试 POST 即可，不需要先查 ID |
| 客户端在 accept 后被杀 | 服务端继续解析 | 重启后按本地 `ingestID` 轮询 |

`X-RAI-Ingest-Retry: 1` 只允许把 `rejected && retryable && attempts < max` 的行重置为 `accepted`，并清空 `next_attempt_at`；不得重置 `committed` 或 `superseded`，也不得改变 `ingest_seq`。

### 4.5 错误分类

| 错误 | 同步/异步 | 可重试 | 说明 |
|---|---|---|---|
| `unsupported_payload` | 同步（词法/信封）或异步（核心字段） | 否 | 包本身不合法 |
| `source_policy_excluded` | 异步 | 否 | 来源不是 Apple Watch |
| `workout_identity_conflict` | 异步 | 否 | 同 UUID 核心事实不同 |
| `sample_identity_conflict` | 异步 | 否 | 子样本身份冲突 |
| `sample_deleted` | 异步 | 否 | 子样本墓碑 |
| `workout_deleted` | 异步 | 否 | Workout 墓碑，删除优先 |
| `bundle_too_large` | 同步或异步 | 否 | 超过既定上限 |
| `dataset_epoch_changed` / `collector_fenced` / `dataset_retired` | 异步（解析时复核） | 否 | 会话已失效，需要重新握手 |
| DB 超时 / 死锁 / 序列化失败 | 异步 | 是 | 指数退避重试 |
| worker 崩溃 / 租约过期 | 异步 | 是 | 自动重新认领 |
| 重试耗尽 | 异步 | 是（人工） | `ingest_retry_exhausted`，保留载荷供诊断 |

分类函数放在 `syncing` 包，例如 `func IngestRetryable(error) bool`；不要按字符串匹配。

### 4.6 v4 兼容

- `POST /v2/sync/workout-bundles` 与 `GET /v2/sync/workout-bundles/{id}` **完全不变**。
- v4 客户端不会看到 `workoutIngestVersion`，继续同步等待提交。
- 服务端保留 v4 路径，直到确认没有旧客户端；删除是后续独立清理，不夹在本项目里。
- v5 客户端一旦收到 `accepted`，**禁止回退到 v4 重传**；否则会造成双写。只有“尚未 accept”的失败才允许回退。

### 5.2 Schema（migration 00050）

```sql
-- +goose Up
-- 接收队列刻意不建 datasets 外键：接收路径必须在任何 dataset 行锁
-- （workout import、training/model publication、job claim）之外完成。
-- 外键的 FOR KEY SHARE 会与 SELECT ... FOR UPDATE 冲突，把秒回拖成 10 秒。
-- dataset 是否存在、epoch/collector 是否有效，在接收时只读校验，
-- 并在解析事务取 dataset 行锁后再次校验。

CREATE SEQUENCE workout_ingest_seq AS bigint START 1;

CREATE TABLE workout_ingests (
    dataset_id        uuid        NOT NULL,
    ingest_id         uuid        NOT NULL,
    ingest_seq        bigint      NOT NULL DEFAULT nextval('workout_ingest_seq'),
    workout_uuid      uuid        NOT NULL,
    bundle_sha256     bytea       NOT NULL CHECK (octet_length(bundle_sha256) = 32),

    -- 接收时写入的精确字节；committed/superseded 后置 NULL，由 workout_imports
    -- 保存投影源。rejected 行保留到保留期结束，便于诊断。
    payload           bytea,
    payload_bytes     integer     NOT NULL CHECK (payload_bytes >= 0),

    state             text        NOT NULL DEFAULT 'accepted'
                      CHECK (state IN ('accepted','committed','superseded','rejected')),
    attempts          integer     NOT NULL DEFAULT 0 CHECK (attempts >= 0),
    next_attempt_at   timestamptz NOT NULL DEFAULT now(),
    lease_until       timestamptz,
    fencing_token     bigint      NOT NULL DEFAULT 0,
    last_error_code   text,
    retryable         boolean     NOT NULL DEFAULT false,

    accept_receipt    jsonb       NOT NULL,
    commit_receipt    jsonb,
    superseded_by     uuid,

    accepted_at       timestamptz NOT NULL DEFAULT now(),
    parse_started_at  timestamptz,
    finished_at       timestamptz,
    updated_at        timestamptz NOT NULL DEFAULT now(),

    PRIMARY KEY (dataset_id, ingest_id),
    UNIQUE (dataset_id, workout_uuid, bundle_sha256),
    CHECK (state <> 'committed' OR commit_receipt IS NOT NULL),
    CHECK (state <> 'superseded' OR superseded_by IS NOT NULL),
    CHECK (state <> 'accepted' OR payload IS NOT NULL)
);

-- 认领：只扫 accepted，按 seq FIFO；next_attempt_at 让重试不堵住新包。
CREATE INDEX workout_ingests_ready
    ON workout_ingests (next_attempt_at, ingest_seq)
    WHERE state = 'accepted';

-- 配额与同 Workout 最新包查询。
CREATE INDEX workout_ingests_pending_dataset
    ON workout_ingests (dataset_id, ingest_seq)
    WHERE state = 'accepted';

CREATE INDEX workout_ingests_workout
    ON workout_ingests (dataset_id, workout_uuid, ingest_seq DESC);

-- 终态清理。
CREATE INDEX workout_ingests_terminal_gc
    ON workout_ingests (finished_at)
    WHERE state IN ('superseded','rejected');

-- No Down: 接收回执与解析状态是审计事实，不做应用回滚删除。
```

设计说明：

- **`payload` 用 `bytea` 而不是 `jsonb`。** 接收事务不做 JSONB 解析/规范化，插入更快；解析时在 Go 里解码，再把 `workout_imports.payload` 写成 jsonb。这样接收路径的 CPU 与 DB 开销最小。
- **`payload_bytes` 单独存。** 配额统计不用 `octet_length(payload)` 去 detoast 大字段。
- **`accept_receipt` 与 `commit_receipt` 分开。** 前者在接收时写入且不变；后者只在解析提交时写。
- **终态后 `payload = NULL`。** 避免和 `workout_imports.payload` 长期双份存储；`rejected` 保留到保留期。
- **无 `datasets` 外键是有意为之。** 迁移注释必须写清楚，代码评审要检查；用 GC 清理孤立行。
- **字节级限制。** 接收表在终态前保存精确字节；提交后 `workout_imports.payload` 仍是现有 jsonb（保留字段值，不保留原始 key 顺序/空白）。若未来需要字节级回放，另立项目增加归档列，不在本项目里改现有表。

### 5.3 接收事务

伪代码：

```go
func (s *Store) AcceptWorkoutIngest(ctx, p Principal, raw []byte, digest string, envelope Envelope) (Receipt, error) {
    // 1) 只读校验：不取 FOR UPDATE，不插入任何带 datasets 外键的行。
    meta, err := s.readDatasetForIngest(ctx, p, envelope.DatasetID)
    if err != nil { return Receipt{}, err } // epoch/retired/collector
    if !p.CanCollect { return Receipt{}, Fail(403, "read_only_device") }

    // 2) 配额：只读计数，允许少量并发超限（有 upload slot 兜底）。
    if err := s.checkIngestQuota(ctx, p.DatasetID); err != nil { return Receipt{}, err }

    // 3) 短事务：只写 workout_ingests。
    tx, err := s.begin(ctx)
    ...
    ingestID := syncing.NewID()
    receipt := syncing.NewAcceptReceipt(ingestID, envelope.WorkoutID, digest, time.Now().UTC())
    var row struct{ ... }
    err = tx.QueryRow(ctx, `
        INSERT INTO workout_ingests
          (dataset_id, ingest_id, workout_uuid, bundle_sha256, payload, payload_bytes, accept_receipt)
        VALUES ($1,$2,$3,decode($4,'hex'),$5,$6,$7)
        ON CONFLICT (dataset_id, workout_uuid, bundle_sha256) DO NOTHING
        RETURNING ingest_id, ingest_seq, state, accept_receipt`,
        p.DatasetID, ingestID, envelope.WorkoutID, digest, raw, len(raw), receiptJSON).Scan(...)
    if errors.Is(err, pgx.ErrNoRows) {
        // 同字节已接收：返回原回执，不重复排队。
        return s.loadAcceptReceipt(ctx, p.DatasetID, envelope.WorkoutID, digest)
    }
    ...
    return receipt, tx.Commit(ctx)
}
```

要点：

- `readDatasetForIngest` 用普通 `SELECT`，**没有 `FOR UPDATE`**；校验 `dataset == p.DatasetID`、`epoch`、`retired_at`、`collector_leases`/`devices`。epoch/collector 的最终裁决仍在解析事务里。
- 不插入 `jobs`，不更新 `datasets.commit_rev`，不写 `change_events`。
- 不调用 `DecodeWorkoutBundleV4JSON` 的完整投影；只调用 `decodeV4Envelope`（词法、重复键、深度、必需字段、时间范围、ID 合法性）。
- 接收事务的提交就是“字节已持久化”的证明；HTTP 处理器在提交成功后才写 200。
- 同字节并发 POST：`ON CONFLICT DO NOTHING` + 回读；只有一个 ingest 行。
- 如果接收集成到 `workout_ingest` 失败，返回 5xx；客户端拿不到接收回执，会重试同字节。

**为什么不在接收时分配 `commit_rev`？** `commit_rev` 是事实提交序号，必须由解析事务在 dataset 行锁内分配。接收只分配 `ingest_seq`，用于同 Workout 的“最新者胜”。

### 5.4 解析队列与 worker

#### 5.4.1 认领

```sql
WITH candidate AS (
    SELECT dataset_id, ingest_id
    FROM workout_ingests
    WHERE state = 'accepted'
      AND attempts < $1
      AND next_attempt_at <= now()
      AND (lease_until IS NULL OR lease_until < now())
    ORDER BY ingest_seq
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE workout_ingests i
SET lease_until      = now() + interval '60 seconds',
    fencing_token    = i.fencing_token + 1,
    attempts         = i.attempts + 1,
    parse_started_at = COALESCE(i.parse_started_at, now()),
    updated_at       = now()
FROM candidate c
WHERE i.dataset_id = c.dataset_id AND i.ingest_id = c.ingest_id
RETURNING i.dataset_id, i.ingest_id, i.workout_uuid, i.bundle_sha256,
          i.ingest_seq, i.payload, i.fencing_token, i.attempts;
```

- 只锁 `workout_ingests` 的候选行，**不锁 datasets**。
- `SKIP LOCKED` 允许未来多 worker 并发认领不同行；同一 dataset 的事实提交仍由解析事务的 dataset 行锁串行化。
- `next_attempt_at` 过滤保证重试包不会永远堵住新包。
- `attempts < $1` 与 5.4.3 的清理共同保证达到上限的包不会被再次认领；认领成功即 `attempts += 1`。

#### 5.4.2 续租

```sql
UPDATE workout_ingests
SET lease_until = now() + interval '60 seconds', updated_at = now()
WHERE dataset_id = $1 AND ingest_id = $2
  AND state = 'accepted' AND fencing_token = $3
  AND lease_until > clock_timestamp();
```

续租失败 → 取消解析 context；最终提交的 fencing 检查也会失败。

#### 5.4.3 崩溃恢复

worker 每 15 秒执行：

```sql
UPDATE workout_ingests
SET lease_until = NULL, updated_at = now()
WHERE state = 'accepted' AND lease_until < now();

UPDATE workout_ingests
SET state = 'rejected', retryable = true,
    last_error_code = 'ingest_retry_exhausted',
    lease_until = NULL, finished_at = now(), updated_at = now()
WHERE state = 'accepted' AND attempts >= $1 AND lease_until IS NULL;
```

然后正常认领。崩溃不会丢包：`payload` 在接收事务里已经持久化。

#### 5.4.4 为什么不用现有 `jobs` 表

现有 `jobs` 有 `datasets` 外键，`ClaimJob` 还会 `FOR UPDATE OF d` 锁 dataset。接收时插入 `jobs` 会：

1. 取 `datasets` 的 `FOR KEY SHARE`，与正在解析的 `FOR UPDATE` 冲突；
2. 把接收请求堵在 10 秒导入后面。

把解析任务放进 `workout_ingests` 自己的行上，接收路径只写一张无外键表，才能保证 G3。

分析 job（`analysis.workout`）仍然在**解析事务内**写入 `jobs`。此时已经持有 dataset 行锁，是同一事务，不会被自己阻塞。

#### 5.4.5 worker 形态

- `cmd/rai worker` 启动两个循环：
  - 现有 `jobs.Run`：分析、训练、模型等；
  - 新增 `ingest.Run`：解析 v5 接收包。
- 默认 `RAI_INGEST_WORKERS=1`。解析是 CPU + DB 重活，单用户部署 1 个足够；多用户再按队列年龄扩。
- 两个循环各自有独立的租赁/恢复，互不阻塞。
- 不把解析塞进 HTTP 进程的请求 goroutine；API 重启不影响已接收的包。

### 5.5 解析事务

把现有 [ImportWorkoutBundle](../../apps/server/internal/storage/postgres/workout_bundles.go) 拆成：

```go
// 同步 v4 路径：解码已完成，开事务，走同一核心。
func (s *Store) ImportWorkoutBundle(ctx, p, bundle, raw) (json.RawMessage, error)

// 异步 v5 路径：解码 + 事务 + 更新 ingest 状态。
func (s *Store) CommitWorkoutIngest(ctx, lease IngestLease) (Receipt, error)

// 两者共用：
func (s *Store) importWorkoutBundleTx(ctx, tx, p, bundle, raw, digest, ingestID string) (Receipt, error)
```

`importWorkoutBundleTx` 保持现有顺序与语义：

1. `ValidateWorkoutBundle`；
2. `SET LOCAL statement_timeout / transaction_timeout / plan_cache_mode`；
3. `lockDataset`（`FOR UPDATE`，此处可以等；等的是解析，不是接收）；
4. 墓碑检查：
   - Workout 墓碑 → `workout_deleted`；
   - 子样本/route 墓碑 → `sample_deleted` / `route_deleted`；
5. **最新者胜检查**：
   ```sql
   SELECT EXISTS (
     SELECT 1 FROM workout_ingests
     WHERE dataset_id=$1 AND workout_uuid=$2
       AND state='committed' AND ingest_seq > $3
   )
   ```
   为真 → 本包 `superseded`，不写事实，并在同一事务写：
   ```sql
   UPDATE workout_ingests
   SET state='superseded', superseded_by=$4, payload=NULL,
       finished_at=now(), lease_until=NULL, updated_at=now()
   WHERE dataset_id=$1 AND ingest_id=$2 AND state='accepted'
     AND fencing_token=$3 AND lease_until > clock_timestamp();
   ```
6. 身份冲突检查、series/route identity；
7. 删除证据、`checkBundleDeletions`、observation；
8. 同字节历史回执检查；
9. 写 workout / samples / associations / series / routes；
10. 写 `dirty_scopes`、`analysis.workout` job、`change_events`、`datasets.commit_rev`；
11. 写 `workout_imports`（最终回执 + payload jsonb）；
12. **fencing + 终态更新**：
    ```sql
    UPDATE workout_ingests
    SET state='committed', commit_receipt=$4, payload=NULL,
        finished_at=now(), lease_until=NULL, retryable=false,
        last_error_code=NULL, updated_at=now()
    WHERE dataset_id=$1 AND ingest_id=$2 AND state='accepted'
      AND fencing_token=$3 AND lease_until > clock_timestamp();
    ```
    影响行数必须为 1；否则 `ROLLBACK`，不得提交事实；
13. `tx.Commit`。

顺序上的两个关键点：

- **墓碑检查必须在最新者胜检查之前。** 删除优先；已删除的 Workout 不应因为“有更新的包”而被报告成 superseded。
- **fencing 更新必须在事务最后。** 它既是状态更新，也是“租约仍有效”的 CAS；失败则整笔事实回滚。

解析错误处理：

- 事务已回滚后，另开一个短事务写终态：
  - 永久错误：`state='rejected', retryable=false, last_error_code, commit_receipt=NULL, finished_at=now()`；`payload` 保留。
  - 可重试且未耗尽：`lease_until=NULL, next_attempt_at=now()+backoff, last_error_code, retryable=true`；仍是 `accepted`。
  - 重试耗尽：`state='rejected', retryable=true, last_error_code='ingest_retry_exhausted'`。
- 终态更新必须带 `fencing_token` 与 `state='accepted'`，防止僵尸 worker 覆盖新租约。
- 不允许把错误文本直接写库或日志；只写错误码。

### 5.6 保留、清理与配额

| 数据 | 保留 | 处理 |
|---|---|---|
| `committed` / `superseded` 的 `payload` | 0 | 终态事务里置 `NULL` |
| `rejected` 的 `payload` | 7 天 | 定时 GC |
| `workout_ingests` 终态行 | 90 天 | 定时删除；`workout_imports` 仍保留最终回执 |
| `accepted` 超过 24 小时 | — | 告警；不自动删除（可能是 worker 停机） |
| 无 `datasets` 对应行 | — | GC 删除孤立行 |

GC 建议作为 admin/worker 的周期任务，不进入 HTTP 路径：

```sql
DELETE FROM workout_ingests
WHERE state IN ('superseded','rejected')
  AND finished_at < now() - interval '90 days';

UPDATE workout_ingests
SET payload = NULL, updated_at = now()
WHERE state = 'rejected'
  AND finished_at < now() - interval '7 days'
  AND payload IS NOT NULL;
```

配额（接收时只读检查）：

- 每 dataset `accepted` 行数 > 200 → 429 `ingest_backlog_full`；
- 每 dataset `accepted` 的 `payload_bytes` 总和 > 512 MB → 429；
- 全局接收并发继续用现有 upload slots；
- 响应带 `Retry-After`，客户端按它退避。

新增指标：

| 指标 | 类型 | 用途 |

| `workout_ingest_accept_total` | counter | 接收成功/拒绝 |
| `workout_ingest_accept_ms` | histogram | 接收事务总耗时（不含读 body） |

| `workout_ingest_pending` | gauge | 当前 `accepted` 行数 |
| `workout_ingest_oldest_age_s` | gauge | 最老 `accepted` 的年龄 |
| `workout_ingest_wait_ms` | histogram | `accepted_at` → 解析开始 |
| `workout_ingest_parse_ms` | histogram | 解析事务耗时 |
| `workout_ingest_committed_total` | counter | 成功 |
| `workout_ingest_superseded_total` | counter | 被更新包覆盖 |
| `workout_ingest_rejected_total{code}` | counter | 永久失败 |
| `workout_ingest_retry_total` | counter | 可重试失败 |

日志：

```text
workout_ingest_accept  ingest_id=... workout_hash=... bytes=685509
                       envelope_ms=... store_ms=... ack_total_ms=...
                       queue_depth=... status=accepted

workout_ingest_parse   ingest_id=... attempt=... wait_ms=...
                       parse_ms=... phases={...} status=committed
```

- 不记录 payload、GPS、心率、样本值、token。
- `workout_hash` 用短哈希，避免把 UUID 直接当高基数标签。
- 告警：
  - `workout_ingest_oldest_age_s > 60` 持续 2 分钟；
  - `workout_ingest_pending > 50`；
  - `workout_ingest_rejected_total` 5 分钟比例 > 2%；
  - worker 心跳缺失 30 秒。

### 5.8 安全

- 接收和状态端点都走现有 Bearer 鉴权与 `Principal`；
- dataset 必须等于 principal 的 dataset；跨 dataset 一律 403/404；
- `ingestID` 不能作为唯一授权凭据，必须 `WHERE dataset_id=$principal.DatasetID AND ingest_id=$1`；
- 接收阶段拒绝重复 JSON key、超深嵌套、非法 UTF-8（沿用 `decodeV4Envelope`）；
- gzip 解压上限、multipart 上限、JSON 深度上限沿用现有实现；
- 状态响应不含原始载荷；
- 队列积压时优先 429，不接受无界写入。

| `.preparing` | 读 HealthKit / 构建 |
| `.uploading` | POST 中 |
| `.accepted` | 接收回执已校验；可离开页面 |
| `.acknowledged` | 最终回执已校验；事实已提交 |
| `.analyzing` | 分析未出结果 |
| `.published` / `.partial` | 分析完成 |
| `.failed` / `.deleted` | 失败 / 删除 |

### 6.3 ACK 校验

新增两个校验器，避免把两种回执混用：

```swift
public enum WorkoutIngestACK {
    static func validateAccepted(_ receipt: JSON, workoutID: String, bundleHash: String) throws {
        // version == 1
        // ingestID 是 UUID
        // workoutID / bundleSHA256 匹配
        // ingestStatus == "accepted"
        // acceptedAt 存在
    }

    static func validateStatus(_ status: JSON, ingestID: String, workoutID: String, bundleHash: String) throws {
        // ingestStatus ∈ {accepted, committed, superseded, rejected}
        // committed 时校验 commitRevision / counts / analysisStatus / analysisJobIDs
        // rejected 时校验 errorCode / retryable
        // superseded 时校验 supersededBy（若提供）
    }
}
```

- v4 的 `WorkoutBundleACK.validate` 保留原样。
- `OutboxStore.acknowledgeIngest` 只接受 `validateAccepted`。
- `OutboxStore.acknowledgeBundleCommit` 只接受 `validateStatus` 的 committed 分支。
- `superseded` 走成功终态，不走 committed 分支。

### 6.4 Outbox 状态转换与 watermark

拆成三个方法：

```swift
func acknowledgeIngest(_ id: String, receipt: JSON) throws
func acknowledgeBundleCommit(_ id: String, status: JSON) throws
func failIngest(_ id: String, status: JSON) throws
```

`acknowledgeIngest`：

1. 校验接收回执；
2. `uploadReceipt = receipt`，`ingestID`、`ingestState = accepted`、`ingestAcceptedAt`；
3. `phase = .accepted`；
4. **释放 bundle 文件**（服务端已有权威字节）；
5. 按 `captureManifest` 推进 `deliveredGeneration`，与 v3 的 ACK 规则一致；
6. 清空 `captureManifest` / `bundleDeletionEventIDs`（与现有 ACK 后清理一致）；
7. 写 `lastACK`。

`acknowledgeBundleCommit`：

1. 校验最终回执；
2. `commitReceipt = status`，`ingestState = committed`，`ingestCommittedAt`；
3. `phase = .acknowledged`，`acknowledgedAt = ingestCommittedAt`；
4. 不要求 bundle 文件仍在；
5. 触发分析 follow-up。

`failIngest`：

1. `ingestState = rejected`；
2. `phase = .failed`，`errorCode = errorCode`；
3. `ingestRetryable` 决定 UI 是否展示“重试解析”；
4. 不自动重建、不自动重传。

**watermark 修复（硬性）**

v5 的 `setBundle` 必须与 v3 路径一致：

```swift
try await store.setBundle(
    id, file: file, sha256: hash, boundary: boundary,
    discoveryGeneration: discoveryGeneration,
    manifest: manifest
)
```

否则 `acknowledgeIngest` 仍会把 `deliveredGeneration` 留在 0，`needsDelivery()` 继续为真，恢复流程再次上传——这会直接抹掉秒回收益。

### 6.5 状态轮询

新增：

```swift
public enum IngestFollowup {
    public static let delays: [TimeInterval] = [0.5, 1, 2, 4, 8, 15, 30, 60, 120]
    public static func shouldContinue(_ phase: WorkoutSyncPhase) -> Bool {
        phase == .accepted
    }
}
```

`SyncCoordinator.scheduleIngestRefresh(id:api:)`：

- 首次立即查；
- 之后按 delays 退避；
- `committed` → `acknowledgeBundleCommit` → `scheduleAnalysisRefresh`；
- `superseded` → 成功终态，停止；
- `rejected` → `failIngest`，停止；
- 404 → `failIngest(code: ingest_not_found)`；
- 预算耗尽仍 `accepted` → 保持 `.accepted`，等下次前台/恢复，不标失败。

轮询只在**前台**进行；进入后台取消（与现有 `stopAnalysisFollowups` 一致）。下次前台由 `recoverPending` 恢复。

### 6.6 启动 / 恢复

`SyncCoordinator.recoverPending` 增加分支：

```swift
case .accepted:
    do { try await refreshIngest(id: task.workoutID, api: api) }
    catch { /* 状态未到，保留 accepted */ }
    if await store.task(task.workoutID)?.phase == .accepted {
        scheduleIngestRefresh(id: task.workoutID, api: api)
    }
```

- `.accepted` **不得**走 `performSync`，否则会重建并重传。
- `.acknowledged` / `.analyzing` 继续走分析刷新。
- `.uploading` / `.preparing` 仍走原上传恢复。
- 如果本地有 `ingestID` 但服务端返回 404（例如服务端回滚且未保留队列），标 `ingest_not_found`，允许用户“重新同步”；不要静默重传旧字节。

`checkAnalysis(_:)` 也要先判断 `.accepted`：先查 ingest 状态，再查分析。

### 6.7 同步入口与 UI

`RAIApp.syncWorkouts(_:)`：

- 普通同步 → `forceNewBundle: false`；
- 新增“重新同步检查迟到数据” → `forceNewBundle: true`；
- 批量同步时，`runWorkouts` 在全部 `accept` 后即可结束：
  - 状态文案：“已上传 N 条，服务器正在后台解析；完成后会自动更新。”
  - 释放 `isIdleTimerDisabled`；
  - 不等待 `published`。

UI 文案：

| phase | 文案 |
|---|---|
| `.preparing` | 正在读取健康数据 |
| `.uploading` | 正在上传 |
| `.accepted` | 已接收，服务器解析中 |
| `.acknowledged` | 已入库，等待分析 |
| `.analyzing` | 分析中 |
| `.published` | 已完成 |
| `.partial` | 部分完成 |
| `.failed` | 具体错误 + 操作 |

“重试解析”只在 `rejected && retryable` 时出现，调用 `POST /v2/sync/workout-ingests/{id}/retry` 或带 `X-RAI-Ingest-Retry: 1` 重发同字节；“重新同步”走 `forceNewBundle: true`，重新读 HealthKit。

> 建议增加一个独立的“重试解析”端点，而不是复用 POST + 头：
> `POST /v2/sync/workout-ingests/{ingestID}/retry`，请求体为空，语义明确、权限好审。
> 若不想加端点，再用 header。

### 6.8 旧版本与回滚

- `workoutIngestVersion` 缺失 → v4 路径，行为完全不变。
- v5 accept 后，即使状态轮询失败，也保留 `.accepted`，不降级回 v4 重传。
- 客户端功能开关 `asyncWorkoutIngest` 默认关闭，先测试设备开启，再默认开启。
- 关闭开关后，新任务走 v4；已经 `.accepted` 的任务仍按 ingestID 轮询直到终态（不能丢）。

### 6.9 阶段二：客户端构建优化（可选）

如果目标是把 tap → “已上传”也压到 5 秒左右：

1. **批量 discovery 一次**
   现在每个 `syncOne` 都调用 `discoverChanges(workoutIDs: [id])`，每条 Workout 扫 10 个 quantity type + route。改为整批一次 discovery，共享结果。
2. **route 与 stream 并发读**
   `V4SyncEngine.build` 目前先并发读 10 个流，再串行 `bundleRoutes`。把 route 放进同一个 task group，并加一个 HealthKit 并发上限（例如 6）避免查询互相拖慢。
3. **复用锚点**
   `HKAnchoredObjectQuery` 的 anchor 已经在任务里；对未变化的 Workout，避免重复全量读。
4. **测量**
   增加 `discovery_ms`、`route_read_ms`、`healthkit_read_ms`，按类型拆分，避免只看 `v4_build_ms`。

阶段二不改变服务端契约，可以独立立项；但它不解决“服务器 10 秒入库”，所以不能替代本项目。

## 9. 发布与回滚

### 9.1 发布顺序

1. **Schema 50**：新增表、序列、索引；纯增量，不改旧表。
2. **服务端**：
   - API 增加 `/v2/sync/workout-ingests` 与状态端点；
   - handshake 增加 `workoutIngestVersion: 1`；
   - `worker` 启动 ingest 循环；
   - v4 路径不动。
3. **服务端自检**：
   - 合成数据 POST 一条，确认 accepted → committed；
   - 确认 v4 旧路径仍可用；
   - 确认 dataset 行锁竞争下接收仍快。
4. **iOS 灰度**：
   - `asyncWorkoutIngest` 默认关闭；
   - 测试设备打开，完成 8.3；
   - 再默认打开。
5. **观察**：
   - `workout_ingest_oldest_age_s`、`pending`、`rejected`；
   - 云服务器容器日志；
   - 客户端 accept → committed 时间线。

### 9.2 回滚

| 层级 | 回滚动作 | 注意 |
|---|---|---|
| 客户端 | 关闭 `asyncWorkoutIngest` | 已 `.accepted` 的任务仍须轮询到终态，不能丢 |
| 服务端 API | 保留 ingest 端点，停止能力广告 | 旧客户端走 v4；不要删表 |
| worker | 可回滚到旧镜像，但会停止解析队列 | 回滚前先确认 `pending=0`，或保留一个 v5 worker 排空 |
| schema | 不回滚 | 表是审计数据；遵循现有“无 Down”约定 |

**回滚前检查：**

```sql
SELECT count(*) FROM workout_ingests WHERE state='accepted';
```

必须为 0，或明确接受“这些 accepted 包将在回滚期间滞留”。不要让客户端在回滚后拿到 accepted 却永远等不到 committed。

### 9.3 旧客户端退役

- 观察 v4 `POST /v2/sync/workout-bundles` 的调用量；
- 连续 30 天为 0，且确认无旧版本客户端后，再单独立项删除 v4 同步路径；
- 本项目不删除 v4，不修改 v4 回执结构。

## 11. 风险与待拍板

| 风险 | 影响 | 缓解 |
|---|---|---|
| 接收表无 `datasets` 外键 | 可能产生孤立行 | 接收时只读校验；解析时复核；GC 清理；迁移注释与测试 |
| 解析队列独立于 `jobs` | 多一套租约/恢复逻辑 | 复用现有模式；单测/集成覆盖崩溃、续租、 fencing |
| worker 停机 | accepted 堆积，用户看到“解析中” | 队列年龄告警；worker 与 API 同镜像部署；`RAI_INGEST_WORKERS` |
| 200 后异步失败 | UX 从“请求失败”变“稍后失败” | 明确文案；rejected 可诊断；retryable 提供重试 |
| 双份原始载荷 | 存储短时翻倍 | 终态置 NULL；rejected 7 天 GC；监控表大小 |
| 多设备同 Workout | 旧包可能覆盖新包 | `ingest_seq` 最新者胜；解析事务内检查 |
| 旧客户端误走新路径 | 回执校验失败、重复上传 | 仅 handshake 明确声明才走；v5 accept 后禁止回退 v4 |
| `series` 仍慢 | accepted → committed 仍需 8–12 s | 本项目不承诺后台秒完成；阶段三可做批量写入优化 |
| 客户端构建仍 8–9 s | 用户仍觉得“点了要等” | 阶段二；UI 明确“已接收”与“解析中” |
| 解析事务长时间持 dataset 锁 | 其他 dataset 写等待 | 只影响解析，不影响接收；多用户需多 worker/分片评估 |

**待拍板：**

1. UI 上“同步完成”定义为 **accept** 还是 **commit**？
   建议：accept 即“已上传”，commit/published 用后台状态更新；否则秒回没有产品意义。
2. worker 部署形态：与 API 同容器、同镜像不同进程，还是独立 worker 容器？
   建议：同镜像，`rai worker` 启动两个循环；单用户足够。
3. `rejected` 载荷保留期：7 天是否足够？
   建议：7 天；按表大小与诊断需求调整。
4. 是否在本项目内做阶段二（客户端构建优化）？
   建议：分开立项；本项目先把服务端 ACK 与恢复语义做扎实。
5. 是否保留 v4 同步路径 30 天？
   建议：保留，直到观测到零调用。

### B. RQrun 与 RAI 的语义对照

| 环节 | RQrun | RAI 现状 | RAI 本方案 |
|---|---|---|---|
| 上传粒度 | 一条 Workout 一个 multipart | v4 一条一个 bundle | 不变 |
| 载荷 | 原始明细 JSON，约 641 KB | 原始明细 JSON + gzip，约 685 KB | 不变 |
| 200 含义 | 文件收到 | 事实提交完成 | **字节持久化 + 解析排队** |
| 解析 | 服务端异步 | 请求内同步 | **worker 异步** |
| 状态 | 轮询 `code_apple_source_status` | 分析状态端点 | **ingest 状态 + 分析状态** |
| 幂等 | `apple_health_workout_id` | `(dataset, workout, sha256)` | 不变 |
| 失败降级 | 单项读取失败不阻断整包 | v4 已按流降级 | 不变 |

### C. 回执字段清单

**接收回执**

| 字段 | 类型 | 必有 | 说明 |
|---|---|---|---|
| `version` | int | 是 | ingest lane 版本，当前 1 |
| `ingestID` | uuid | 是 | 本次接收 ID |
| `workoutID` | uuid | 是 | HealthKit Workout UUID |
| `bundleSHA256` | hex | 是 | 解压后 JSON 的 SHA-256 |
| `ingestStatus` | string | 是 | `accepted` |
| `acceptedAt` | RFC3339 | 是 | 接收事务提交时间 |

**最终回执** = 现有 `WorkoutImportReceipt` + `version` + `ingestID` + `acceptedAt` + `committedAt`。

**状态响应** = 最终回执可选字段 + `attempts` + `updatedAt` + `retryable` + `supersededBy`。

### D. 术语

| 术语 | 含义 |
|---|---|
| 接收 / accept | 原始字节 + 接收回执 + 队列行提交 |
| 解析 / commit | 事实、删除屏障、日志、分析 job、最终回执提交 |
| ingest lane | 新增的异步接收协议路径 |
| 最终回执 | `ingestStatus=committed` 的回执 |
| `ingest_seq` | 接收顺序号，用于同 Workout 最新者胜 |
| `commit_rev` | 事实提交序号，仍由 dataset 行锁分配 |
| fencing | 解析租约令牌；终态更新失败则回滚事实 |
