# RAI Workout v6 前台手动上传实施方案

**状态：待实施。本文只交付方案，不授权执行代码修改、测试、数据库操作或部署。**

决策日期：2026-11-10。

适用场景：个人使用 Apple Watch 自带“体能训练”App 跑步，记录同步到 iPhone HealthKit，再由用户在 RAI 中点击上传。

本方案采用 RQrun 抓包文档中可观察到的“选择记录、一条跑步一个 JSON、一次上传、服务端异步处理”方式，并按用户决定进一步简化客户端。RQrun 的后台、失败重试、服务端幂等和故障处理细节未经该抓包验证，本文相关规则是 RAI 自己的设计。

## 1. 目标与实施边界

| 环节 | 目标行为 |
| --- | --- |
| 触发 | 只在用户点击“同步”时上传。启动、回到前台和 HealthKit 变化不自动上传。 |
| 选择记录 | 查找符合来源要求的跑步记录，支持单选、多选和批量上传。 |
| 组包 | 每条 Workout 获取一次核心信息，每种关联指标查询一次，生成一个 v6 JSON。 |
| UUID | 上传 JSON 中的 HealthKit 对象标识只保留顶层 `workoutID` 一次。 |
| 上传 | 每条跑步一个 POST 请求，可 gzip 压缩。 |
| 最终结果 | 每条记录只显示“上传成功”或“上传失败”；批量显示成功、失败数量。 |
| 中断或失败 | 本次结束。下次点击时重新读取、重新组包并尝试上传。 |
| 客户端持久任务 | 不保存 Workout 待上传队列，不恢复上传，不跨启动续传。 |
| 服务端处理 | 可靠保存原始包后确认上传成功，事实投影和分析由 Worker 处理。 |

“正在读取”“正在上传”和 `已完成 n/N` 是本次操作的临时进度，不是持久同步阶段。初始列表可以显示“未上传”，但一次上传的最终结果只有成功和失败。

本方案收敛 Workout 上传流程。日常健康、睡眠和 VO₂ 的数据格式及 anchor/回执协议不在本次重写范围；它们的上传入口也只能由用户点击触发，不再借启动、前台恢复或观察回调自动投递。它们仍按各自合同管理批页和游标，不能因删除 Workout Outbox 而一并清空共享状态。

用户此前提出的空白目标库、独立新会话和历史重新导入作为未来切换前提保留。本文不执行建库、重置身份、搬迁或清理旧数据；历史记录的导入也必须由用户在前台选择后点击执行。

## 2. 当前状态与旧方案关系

当前工作区已有 v6 按类型数组组包、每个 Workout 一个请求、gzip、服务端 UUID 去重、原始字节接收及异步 Worker 基础。当前代码仍有后台 URLSession、Outbox、自动重试、启动/前台恢复和多阶段同步 UI，尚未达到本方案目标。

上一轮已产生一组“移除活动分段 UUID、服务端生成活动内部身份”的代码和合同修改。定向 Go 用例、隔离 PostgreSQL v6 用例、SwiftPM v6 用例和 Go 完成门禁有通过记录，但模拟器 `RawStreamSyncEngineTests.testBuildEmitsProtocolSixWithoutPerSampleIdentity` 失败，尚未排查修复。因此 UUID 目标也不能登记为完成验收。本轮只编写文档，不继续修复或执行测试，也不回滚既有工作区改动。

本文取代 [v6 全量重传与同步优化方案](WORKOUT_SYNC_V6_REIMPORT_PLAN.md) 中客户端自动发现待办、后台恢复、耐久 Outbox、自动续跑、多阶段同步结果及上传前完整性证明的目标。旧文保留为历史，不再按旧客户端流程继续实施。服务端原始字节、事务、删除屏障和真实分析要求继续遵守工程约定。

## 3. 用户操作与前台生命周期

### 3.1 选择与提交

1. 用户进入同步页面，读取 HealthKit 跑步概要列表。列表查询不自动启动明细读取或上传。
2. 复用现有 Apple Watch 原生跑步来源策略。明确排除的记录不能勾选，无法分类的记录显示原因，不猜测为合格来源。
3. 支持按页加载历史记录；现有“最近 100 条”的展示范围不能成为历史上传总量上限。“选择本页”和“选择全部符合条件记录”明确区分。
4. 用户点击“同步所选记录”后，固定本次所选 UUID 集合，建立仅在内存中存在的操作上下文。
5. 每轮操作握手一次，所有所选记录复用同一服务、dataset、epoch、鉴权和限额上下文。身份失效时失败退出，不自动切换身份后继续上传。
6. 首版按一条接一条处理，不增加并发配置或持久调度器。单条失败后可继续处理本轮其他所选记录。
7. 全部结束后显示“上传成功 X 条，上传失败 Y 条”。每条失败给出简短原因；用户可重新选择失败项，再次点击。

服务端已有记录列表可以辅助显示“已上传”和减少重复选择，但不是上传前的必需对账流程。不要求为每条记录先 GET 状态，更不要求全库摘要、完整性清单或下载游标。

### 3.2 离开前台与中断

- 取消本轮操作、关闭上传页或 App 进入后台时，取消未完成的读取和上传，停止启动后续记录。不申请额外后台执行时间，不建立后台 URLSession。
- 短暂进入 inactive，例如系统授权弹窗，不等同于进入后台，不因此错误取消授权流程。
- 本轮已收到有效确认的记录保留“上传成功”。未确认或尚未开始的所选记录计为“上传失败”，原因可显示“本次上传已中断”。批量统计始终覆盖本轮所选集合。
- 杀进程后不恢复本轮任务。再次打开只显示普通记录列表，由用户重新选择并点击。
- 连接中断、超时、429、5xx 或授权失败后，本轮不自动重试、不等待重连、不进入倒计时。429 可以提示“请稍后再次点击同步”。
- 请求取消不代表服务器一定没有保存。用户下一次点击同 UUID 时，由服务器去重，不由客户端恢复上次传输。

## 4. v6 载荷：HealthKit UUID 只在顶层一次

### 4.1 身份规则

| 对象 | 上传 JSON 中的身份 |
| --- | --- |
| `HKWorkout` | 只写顶层 `workoutID = HKWorkout.uuid`。 |
| Workout 核心 | 不再写 `uuid` 或 `workoutID`。 |
| 活动分段 `HKWorkoutActivity` | 不上传分段 UUID，不重复 Workout UUID。 |
| 标量样本 | 只写时间和值，不上传样本 UUID。 |
| series 父组及点 | 父组嵌套点数组，不上传父样本 UUID、点 UUID 或 Workout UUID。 |
| 路线及轨迹点 | 只写点数组，不上传 route UUID，不重复 Workout UUID。 |
| 会话 | `datasetID`、`datasetEpoch`、`collectorEpoch` 仍是顶层会话字段；它们不属于 HealthKit 对象 UUID。 |

HealthKit UUID 可以用于读取时的内存查询、分组和排序，但不生成逐样本 UUID 映射文件，不建立跨包子对象身份对账。Workout 来源描述符中的 bundle identifier 按来源语义保留，不把它误当成对象 UUID 删除。

继续使用 `POST /v2/sync/workout-ingests/{workoutID}`。URL 路径用于定位和校验，同一个 Workout UUID 在 JSON 内只出现于顶层 `workoutID`；本次不为减少 URL 中的标识而另建上传接口。

### 4.2 载荷结构示意

下面是结构示意，省略会话与时间字段的实际值，不是可直接发送的测试包。

```json
{
  "protocolVersion": 6,
  "datasetID": "<datasetID>",
  "datasetEpoch": "<datasetEpoch>",
  "collectorEpoch": "<collectorEpoch>",
  "workoutID": "<HKWorkout.uuid>",
  "startUs": 0,
  "endUs": 60000000,
  "source": {
    "bundleID": "com.apple.health",
    "productType": "Watch7,1"
  },
  "workout": {
    "activityType": 37,
    "durationUs": 60000000,
    "activities": [
      {
        "startUs": 0,
        "endUs": 60000000,
        "durationUs": 60000000,
        "configuration": {
          "activityType": 37,
          "locationType": 3,
          "swimmingLocationType": 0
        }
      }
    ]
  },
  "streams": [
    {
      "type": "HKQuantityTypeIdentifierHeartRate",
      "unit": "count/min",
      "samples": [[0, 1000000, 120]]
    }
  ],
  "routes": [
    {
      "points": [[0, 31.2, 121.4]]
    }
  ]
}
```

标量沿用 `[startDeltaUs, endDeltaUs, value]`，路线沿用 v6 点元组，series 沿用父组头加点数组。活动分段保留时间、时长、配置、统计和事件，移除 UUID 不得导致分段丢失。

数据库若仍要求样本、series 父、路线或活动 UUID，统一由服务端按 dataset、Workout、事实种类、类型及原数组下标生成。被跳过的坏条目仍占原下标，不能把后续条目的身份前移。这些是数据库内部标识，客户端不传、不维护。

### 4.3 读取质量与缺失值

- 每次尝试对 Workout 核心读取一次；每种标量、series 查询一次；枚举路线并将返回路线读取到结束。这里的“一次”不表示 HealthKit 提供跨类型原子快照。
- 已知、受支持的流正常查询且返回零条，作为当前可见范围内的空结果。室内跑步没有路线等情况不因此失败。
- 任一已启动的指标查询报错、路线读取中断或条目/点数/字节超限，本条失败，不将错误静默变成空流或空路线后永久接收。
- 合同允许跳过的已知坏点按既有规则处理，可记录计数与诊断；未知字段、流、样本或点继续保留在服务器收到的原始包中，不阻断整个包。
- 缺失不是零值，也不等于用户拒绝授权；不能据此宣称历史完整或所有明细已到齐。

## 5. 一条记录一次请求

### 5.1 本次操作内的数据

读取完成后序列化一次。需要压缩时从该 JSON 派生一次 gzip，再装入 multipart 的单个 `file` part。

仅使用内存和本次请求所需的临时文件。临时文件不登记为待上传任务，不保存重试时间、后台传输标识、断点或恢复索引；结束后释放，进程中断残留的临时文件只能清理，不能恢复投递。

使用普通前台 URLSession，并配置有限超时；网络不可用直接失败。gzip 不满足压缩大小或解压比限制、但明文仍满足合同限额时，本次选择明文 multipart。一个尝试只选择一种表示，不先上传 gzip 失败后再自动发第二个 POST。

沿用 v6 现有限额：JSON 32 MiB、gzip 8 MiB、解压比 100:1 加 64 KiB 余量、样本及 series 组头合计 50,000、series 点 1,000,000、路线 16 条、路线点 1,000,000。最终以握手和合同一致的边界为准，客户端超限失败，不截断。

### 5.2 上传成功与失败

| 场景 | 本次前台结果 |
| --- | --- |
| 原始包已可靠保存，收到有效 `accepted` 回执 | 上传成功。 |
| 同 UUID 已接收，服务端返回首次接收回执 | 上传成功，不覆盖首次原文。 |
| 读取或组包失败、硬限额、鉴权失败、服务端明确拒绝 | 上传失败，并显示原因。 |
| 超时、断网、取消，或 HTTP 成功但回执无法校验 | 上传失败；说明未获得有效确认，下次可手动尝试。 |
| 接收后 Worker 投影或分析失败 | 已确认的上传结果保持成功；训练详情如实显示处理或分析不可用及原因。 |

**上传成功只表示服务器可靠保存原始包，不表示事实已经提交，也不表示分析已经完成。** 接收事务提交之后才能返回成功，不能仅收到请求、放进进程内存就确认。

校验回执与当前 Workout、会话及返回状态匹配；不能只因 HTTP 200 就显示成功。当前目标是全新数据集，若出现“已有 Workout、没有接收行”的异常，不用通用成功分支掩盖一致性问题。

上传结束不自动 GET 补确认、不轮询 ingest 状态、不等待分析完成。用户进入训练详情时可以读取该页面当前需要的服务端结果，不能由详情读取重新触发上传。客户端不维护 `accepted → committed → analyzing → published` 的持久上传状态机。

### 5.3 手动再试与不可变上传

下次用户点击时允许从 HealthKit 重新获取当前可见数据，不要求恢复上一次文件，也不要求跨点击保持相同字节。

服务端仍以 `(dataset_id, workout_uuid)` 唯一接收。若上次请求已被服务器保存、但手机未收到确认，新请求只返回首次接收回执，不能用本次新生成的内容覆盖首次原文、重复写事实或新增分析任务。

若上次从未被接收，本次新生成的包可成为首次接收包。这个规则保证手动再试安全，无需恢复上传或额外 upload ID、内容哈希身份和子样本去重协议。

## 6. 服务端保持的保障

客户端简化不改变以下服务端要求：

1. 精确保存解压后的原始 JSON 字节，包含空白、键顺序和未知扩展值。只把已知字段投影成事实，不让 JSONB 的表示限制破坏原文接收与后续处理。
2. API 校验身份、根来源、Workout 核心、JSON 结构与资源边界，再在短接收事务持久化原文。重放首次回执，不覆写首次原包。
3. Worker 在事务内提交事实、删除屏障判断、提交日志、分析待办和最终回执；dataset 行锁决定提交顺序，不用 sequence 充当下载水位。
4. 同 UUID 并发、确认丢失、Worker 中断、暂态数据库错误和管理删除保持幂等、防复活和真实故障状态。Worker 内部重试不属于客户端恢复上传，不暴露成同步页面的多阶段流程。
5. 服务端接收后若后续处理失败，不伪装分析完成。是否存在原包、是否已投影及失败原因在服务端可诊断，产品页按真实可用性展示。

不上传 HealthKit 删除，也不根据本轮未选中或快照缺席删除服务器事实。已由管理路径删除的 UUID 继续受删除屏障约束。

## 8. 分析与 Readiness 边界

上传按钮不再生成或续期 Workout completeness 证明，也不为证明而维护全量清单、anchor 待办或多页对账状态。

Readiness 若仍依赖现有证明，缺少证明时继续显示覆盖不足或不可用，不能因“用户点过同步”或“所选全部上传成功”认定健康历史完整。Readiness 的服务端覆盖规则调整作为独立业务工作处理，不阻塞手动上传功能，也不借此把复杂证明流程重新加回客户端。

训练详情的处理/分析状态与同步结果分开。真实分析尚未产生时显示真实原因，Worker 不能用占位结果代替完成。

## 9. 实施顺序与验收

以下步骤仅供用户之后授权实施时执行，本轮不执行。

| 阶段 | 交付 | 放行条件 |
| --- | --- | --- |
| A. 合同与 UUID | 明确一次前台 POST、成功语义和顶层唯一 HealthKit 对象标识；处理上一轮 UUID 模拟器失败项。 | 合成载荷中顶层 Workout UUID 仅一次；活动分段、series、样本和路线无对象 UUID，明细仍可入库。 |
| B. 前台单条上传 | 前台读取、组包、可选 gzip、一次 POST、回执校验、内存结果。 | 单条成功/失败可复现，无状态 GET 补确认、无自动重试、无 Workout 耐久任务。 |
| C. 批量与生命周期 | 选择、历史分页、串行批量、取消和前后台边界、成功失败计数。 | 启动、回前台、HealthKit 通知和重启均不上传；只有再次点击才发请求。 |
| D. 清理与验收 | 移除新流程中的恢复入口与多阶段 UI，更新合同和真实实施记录。 | 本机完成门禁、定向隔离 PG、SwiftPM 和 Simulator 验证；真机验收单独记录。 |

必须覆盖的场景：

- 室内无路线、合法空流可上传；查询失败、路线中断和超限分别导致单条失败。不能把查询故障当成没有数据。
- 带活动分段、series、标量和路线的实际组包路径验证顶层唯一 HealthKit UUID；分段时间、事件和统计完整保留。跳过坏条目后服务端内部身份仍按原数组位置生成。
- 同 UUID 连续手动上传、并发上传、首次已保存但回执丢失，再次手动尝试都返回首次接收结果；原文、事实和分析任务不重复。
- 断网、超时、429、401 和 5xx 不产生自动重试；批量未确认项计入失败，已经成功的项不回退。
- 关闭页面、进入后台、杀进程、重新启动后，没有自动 POST、后台恢复或待上传文件接管。授权弹窗不会错误终止操作。
- 每轮只握手一次；每条 Workout 每次尝试只读取一次核心和各类型明细，只发送一个 POST。压缩回退在发送前确定。
- Worker 延迟或失败时，上传结果与实际分析可用性分别展示，不能把接收成功伪装成分析完成。
- 未知嵌套字段、未知流、坏点及 `1e400`、`\u0000`、额外 `observation` 等扩展值保留原始字节；已知事实仍可投影和读取。

仅使用合成数据，在本机 Mac 执行受影响 Go 测试和 `scripts/local/test.sh gate`；涉及事实提交、删除或接收事务的变更，执行真实隔离 PostgreSQL 集成测试。合同变更运行合同检查，iOS 变更运行受影响 SwiftPM 与 Simulator 用例。性能报告分别记录读取/组包、上传确认与服务端后续处理耗时，不能用小包接收耗时代表完整跑步的点击体验。

真实 iPhone/HealthKit、Watch 到手机的明细可见性、前台生命周期与实际网络体验需单独验收。Simulator 或文件存在不替代真机证据。构建、部署、创建新空库、切换入口和真实历史导入均另行授权。

## 10. 接受的行为边界

- 本次中断后不会自动继续；再次手动操作可能重新读取和上传完整包，这是简化流程的预期行为。
- 首次接收以当时手机 HealthKit 可见数据为准。查询成功不能证明 Watch 的所有关联明细已经到齐；首次接收后才到达的明细不自动补传。
- 手机未收到确认时可能显示失败，而服务器已经保存。再次手动尝试通过 UUID 去重收敛，不以本地失败推断服务端没有数据。
- 上传成功不证明所选之外的历史已经导入，也不证明 Readiness 覆盖满足要求。
